# V3 阶段 0 本地有限样本归因

2026-10-21，源码检查点 `c485cbb`。这是一轮有限2,000次尝试的隔离诊断，不是持续CPS验收，也不能与r19的30秒测量数字作同条件性能比较。协议基础尚未接入准入，实际仍走原lock_compat路径。

## 场景和完整性

真实MySQL8.4.11、Redis与内嵌模拟网关，一台本地Docker Desktop主机；预装QUEUED有限集合，20%确定性模拟接通，每次完整占线20秒，规则AI。主负载实际状态处理至稳定排空约55.934秒；不是固定供给的正式测量窗口。未使用真实SIP/RTP、音频或云模型，也没有目标Linux和外置模拟器对照。

2,000个计划身份全部获得唯一平台确认，与2,000条网关尝试、唯一UUID及唯一K一致；业务身份异常为0。最终预留、号码保护、平台活动计数、语音活动计数均为0，任务/回执/网关回调也全部排空。`storage_calibration_passed=true`只表示该有限集合及排空校验通过；`capacity_qualified=false`保持不变。

实际数据库参数：双1、REPEATABLE-READ、binlog开启、binlog压缩关闭；缓冲池仅16MiB、table_open_cache=4。这些测试容器参数明显不同于V3的目标数据库，必须在目标配置重测后才能作选型或容量归因。

## 已观察到的等待

JFR按本轮负载开始至排空的时间范围裁剪，保留项目调用栈，短于JFR阈值的事件未必录制。下表为线程等待时间，多个线程可能重叠，不是单个全局串行段的持有时间，不能相加后除以墙钟时间计算瓶颈占比或CPS上限。

| 类别 | 事件数 | 累计线程等待 | P95单事件 |
| --- | ---: | ---: | ---: |
| JvmPlatformLock 平台或身份锁 | 476 | 67.986秒 | 428.870ms |
| 网关账本数据库SocketRead | 580 | 26.629秒 | 103.000ms |
| 数据库commit的SocketRead | 124 | 1.842秒 | 26.362ms |

JvmPlatformLock同时承载平台锁与身份锁，当前JFR不能按实际锁键分开。因此可确认该锁路径存在显著等待，不能把全部等待归为平台锁，更不能宣称S1至S5各点占比已量化。网关账本SocketRead也包含普通SQL及锁等待，不能全部归为哨兵锁。

71个`dial_prepare`批次日志显示：获取兼容锁等待P50约10.376ms、P95约372.326ms；锁内取事实、配置、候选处理及flush合计P50约180.197ms、P95约353.189ms，且未包含后续事务提交。候选最多100条，候选不等于成功准入，不按100直接摊薄成每次成本。

数据库摘要中COMMIT共11,480次、累计15.936秒、单次最大40.636ms。该摘要以及文件I/O累计值包含启动、迁移、夹具及负载，不是纯拨号窗口差值；不得与JFR的1.842秒重复相加或由其推导业务吞吐。

## 对实施顺序的影响

保留持久配额/发送栅栏前置，先缩短锁内事实与写入工作，再讨论去锁；不能凭本轮数据删除旧保护。新协议的持久发放、恢复及副作用边界必须在真实事务成本下评价，不能再按纯内存交换估算。

S0仍缺：按锁键区分等待与持有、五个热点的非重叠归因、目标数据库参数的fsync/提交分布、外置模拟器对照、完整HTTP持续供给与全写入者合同。本轮只推进S0证据，不签署S0退出或持续500 CPS通过。
