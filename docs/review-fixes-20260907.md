## 压测环境与口径

所有数据均为本次生成的模拟数据。独立 Docker 网络、PostgreSQL、Redis、API、消费者，仅绑定本机 28000 端口。原业务容器、数据库和录音未用于发压。

控制 API：2 个 Uvicorn 进程，每进程数据库池 10+5；默认准入预算随连接池为 15，即两个进程共约 30 个活动请求名额，不排队等候名额。回调消费者 1 个进程、4 个执行槽。HTTP 发压器在宿主机运行，按固定到达时间调度，有显式等待上限。各档独立通话集合、每档 20 秒。

回调场景使用**已存在且可转换为终态的模拟话单**，实际执行事件去重、状态事务、质检、时长入库与 outbox，并启用独立消费者。外部业务推送关闭，任务走关闭推送的正常完成路径。因此结果不包含外部回调网络延迟、AI 推理、ASR、TTS、RTP 或 PBX 负载。

### 模拟拨号

固定模拟供应商响应时间 200ms，数据库池仅 2 个连接、无 overflow；仅测试进程把平台及租户容量设到对应档位。

| 并发批次 | 成功/失败 | 批次耗时 | 批次平均 CPS | 同时供应商请求峰值 | I/O 等待中 DB 连接最大值 |
|---:|---:|---:|---:|---:|---:|
| 20 | 20 / 0 | 0.317s | 63.12 | 20 | 0 |
| 50 | 50 / 0 | 0.467s | 107.11 | 50 | 0 |
| 100 | 100 / 0 | 0.751s | 133.09 | 100 | 0 |

每档核对了实际 active reservation 数。CPS 是短批次平均值，不是持续拨号速率；100 路档模拟 200ms 网络等待的实测 P95 为 519.60ms，说明同步数据库工作仍会拖延事件循环。F2 的“等待占连接导致池耗尽”已解除，同步调度和租户串行化仍有优化空间。

## 仍存在的容量边界

1. 代码默认平台安全上限仍为 20，100 路仅在独立模拟测试进程显式设置；完成本轮修复不会自动把生产配置提高到 100。
2. 过载直接原因是活动请求名额用完；短事务内仍含多次数据库往返及自动分析，消费者也竞争数据库资源。后续应测量 SQL/锁等待，将自动分析改为可靠异步任务，按数据库预算分配 API 副本与消费者；单纯放大连接池或取消准入保护没有容量保证。
3. 拨号数据库操作仍同步执行，租户准入检查仍串行化。下一阶段应拆分短事务准备、异步线路 I/O、按轮次条件更新，并保持有界线程与请求数。
4. 回调消费的本次结果不代表 AI 消费能力。AI 执行槽、模型/ASR/TTS 配额、PBX 媒体资源、线路通道数及 CPS 都需独立测量；真实 AI 同时通话上限以其中最小值和延迟验收为准。
5. 媒体没有序号的旧供应商只能获得去重、轮次和关闭保护，完整乱序保护依赖升级网关或供应商提供事件顺序信息。
6. 计费是按秒折算估算。实际运营商按分钟取整、供应商计费规则、缺失 CDR 和历史账单对账仍需正式接入验收；缺失数据不计价不等于免费。
