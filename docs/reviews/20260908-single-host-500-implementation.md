# 单服务器 500 在途呼叫开发与验收记录

日期：2026-09-08。开发基线：`10ab8a5d8b6626c46ba2c0175535a4f15a558c9c`，分支：`fix/review-p1-p2-20260907`。

本次完成单机部署候选、容量门禁、媒体故障准入、回调批提交、共享模型额度及测试工具。**600 回调/秒混合压测未达标，不能认定单机 500 路已经满足商用要求。** 代码提交是可继续优化、可复核的开发交付，不能替代真实语音或生产验收。

## 方案口径与实现

采用《单服务器500并发架构与商用评估》及后续硬件修订：500 指呼出、振铃、AI 接通、人工等待/转接/接通等占用中的通话总数。ASR/TTS/LLM 使用云服务。32 专用 vCPU、64 GiB 是首轮测试候选，实际可承载量由目标机测试决定。

| 实现 | 行为与边界 |
|---|---|
| 单机部署模板 | 独立 Compose 文件，6 API、4 AI worker × 160、2 Agent × 320、12 媒体 × 50、1 控制网关、1 FreeSWITCH、1 后台调度；DB/Redis 同机 |
| 资源预算 | 500 业务槽位、600 媒体槽位、640 AI 任务槽位；应用 DB 池总额 64，PostgreSQL 上限 120；容器上限合计 31.5 CPU、51.25 GiB。配置检查不等于性能实测 |
| 拨号准入 | 节点规格允许 500，旧默认值保留；原有平台/租户/任务/线路/预算的较小限额继续生效；并发第 501 路拒绝；未知执行结果继续占位并保留幂等标识 |
| 媒体故障 | 探测有时效；故障或旧代次保留归属并结束旧会话；可配置按健康进程容量接收新呼叫；控制网关拨号前再次核对媒体容量，避免只依赖后台探测缓存 |
| 回调持久化 | 有界队列合并 SQLite FULL 提交，提交成功才 ACK；取消不撤销已接受写入；停机排空写入；保留稳定事件 ID 和同通话事件顺序；增加领取索引及提交/在途指标 |
| 模型账号额度 | 两个 Agent 使用同一持久化 SQLite 账本，保守计量 RPM、估算 TPM、短时请求量及 429/503 冷却；不同预算启动失败；模型网络等待不持有数据库连接 |
| 模型可用性门禁 | 可启用 Agent `/readyz` 探测，额度账本不可用时停止新拨号；探测有周期延迟，已有通话仍按原生命周期处理；该接口明确不验证云模型连通性 |
| 预检与回归 | 区分在途/已接通口径与单机/集群；单机不套用 N-1 预算；新增实际 Compose 渲染测试、共享卷一致性和数据库池预算校验，并接入 CI 定义 |

具体文件、配置顺序、密钥和镜像要求见[部署说明](../../deploy/single-host-500/README.md)。没有自动放大现有租户/线路配额，没有替换运行实例。

## 未通过项：600 回调/秒混合负载

500 个合成通话、每秒 200 个终句与 400 个媒体事件，发压 30 秒，计划共 18,000 个事件。链路包含真实持久化发送队列、NGINX、6 API、PostgreSQL、4 AI worker 和延迟 3 秒的合成模型。不是 SIP/RTP 音频压力实验。事件重试使用原 ID；下表 HTTP 数包含重试，不能当成不同业务事件计数。

| 观测 | 初次 | 增加回调领取索引后 |
|---|---:|---:|
| HTTP 200 | 11,961 | 12,806 |
| HTTP 503 | 11 | 793 |
| HTTP 502 / 504 | 0 / 2 | 17 / 4 |
| 截止时未送达回调 | 6,039 | 5,194 |
| 最老回调年龄 | 80.10 秒 | 77.91 秒 |
| HTTP P99 | 721.49 ms | 645.00 ms |
| 发压调度滞后 P99 | 207.17 ms | 196.49 ms |
| 实验总观察时长 | 100.07 秒 | 99.31 秒 |
| 容量 SLO / 全链路正确性核验 | 未通过 / 未通过 | 未通过 / 未通过 |

证据为 `dialogue-results.json` 与 `dialogue-index-results.json`，包含队列时间序列。截止仍有回调和 AI 任务未完成，不能认定混合负载下所有事件都已完成或恰好处理一次；单元测试中的持久化/重放通过不能替代这项核验。

索引优化并未解决整体吞吐。503 及持续积压仍是性能阻塞；本机 Docker Desktop 代理到宿主进程的连接问题也产生了 502/504。当前证据不能将全部失败归因于代理，也不能据此推算目标 Linux 主机一定达到或达不到 500 路。下一步需在目标 Linux 网络拓扑重放相同负载，结合逐 API 入场等待、数据库锁/连接、回调队列及 AI 调度数据定位，并在调整后重新测试原负载，不降低目标掩盖问题。
