# 单机 500 总在途：问题修复与复验

日期：2026-09-13。范围：云端 ASR/TTS/LLM、32 核 / 64GB 候选方案；沿用 500 个客户呼叫总在途口径。

已修复回调批量投递、启动就绪、共享配额竞争和播放 HTTP 连接池复用问题，并完成回归。**500 个合成会话在目标 50 次终句/秒、10 轮对话下通过本次模拟控制门槛；80 次终句/秒及延长/突发回调测试仍有延迟超标，不能认定单机 500 路已稳定商用。**

本次没有目标 32 核 / 64GB 主机，也没有真实云 ASR/TTS/LLM 与 500 路 SIP/RTP。32 核 / 64GB 仍是待验收候选配置，不能按本机与候选机的核数比例外推容量。

最终 50 档为每会话约 10s 一轮，生成及等待最后回复耗时 103.34s，实际终句数量/该耗时为 48.38 次/秒；5,000 次模型请求、正式回复和模拟播放确认全部完成，失败、模型重试和等待提示音均为零。该轮只能证明这一受控负载和时长。

最终 80 档为每会话约 6.25s 一轮，实际终句数量/生成及等待最后回复耗时为 70.31 次/秒；2,500 次正式回复完成，另产生 31 次等待提示音。虽然没有丢事件或模型失败，但延迟超标，且等待上一轮回复会降低实际发压速度，因此不能报为“80 次/秒稳定通过”。

较早的 80 档曾短轮通过（P99 4,181ms），重复时为 4,497ms、20 轮时为 6,946ms。所有失败结果保留在证据目录中。最终两轮使用同一组当前源码、修正后的观察器和自动清理入口；不能用其中最佳轮次覆盖失败轮次。JSON 中 `capacity_slo_passed` 仅表示回调门槛，必须同时读取 `conversation_control_slo_passed`；真实全链路标志仍为 false。

## 已实施的修复

| 问题 | 修改 | 保留的正确性约束 |
|---|---|---|
| 高频逐事件 HTTP 与事务开销 | 增加有界批量回调，最多 16 条、聚合等待最多 5ms；网关总投递仍为 24 个事件槽位 | 一通话只取一个队首；同 origin；完整签名；按分区固定顺序取锁；整批收件提交后 ACK；逐事件原始身份去重 |
| 批内冲突、队列满、旧接收端兼容 | 接收端返回拆分信号；发送端按原身份逐条隔离重试 | 响应丢失或不完整 ACK 保留全部队首；坏事件不能让同通话后续事件越过 |
| HTTP 错误头丢失 | 保留 HTTPException.headers | Retry-After 与批量拆分信号能够传至调用方 |
| 消费者过早就绪与冷启动 | Inbox 先加载业务处理模块；500 配置要求 6 个活跃消费者；AI 动作线程和模型 HTTP 客户端在报告就绪前准备 | 未完成初始化时不报告就绪；预备阶段不发送模型或播放请求 |
| 两个 Agent 的共享配额账本写入竞争 | 进程内串行写入、空闲 WAL 保持连接、首次 WAL 切换的有界重试 | 跨进程仍共享同一预算；FULL 提交；无事务跨模型等待；提交异常不重放预算预扣 |
| 每条播放命令重建 HTTP 连接池 | 把每次变化的签名、nonce 和凭据放到请求头；复用客户端 | 每次仍产生新的 nonce 和签名，租户、attempt 与请求凭据独立校验 |
| 原压测没有有效回复 | 新增真实 Agent + 共享配额 + 本地模型/播放模拟的闭环；下一轮以正式 AI 回复提交为条件 | 提示音不计为正式回复；记录请求、回复、播放确认、失败、重试、每轮延迟及工作池排队 |

AI 动作线程由每进程 4 调至 8，数据库线程保持 2；应用数据库连接预算仍为 64。每进程 16 动作线程 / 4 DB 线程的对照没有带来收益，已回退。

## 环境与测试口径

- 目标 32 核 / 64GB Linux 尚未实际运行；本次为 Docker Desktop Linux 虚拟机，12 CPUs / 约 7.75GiB，另有原业务容器运行。
- 使用本地运行镜像 `review0910-backend:sniffio`，以只读挂载加载当前代码。每轮记录列明文件的源码 SHA-256、依赖版本，并核对运行期间源码未改变。这不是完整生产镜像的重建或发布。
- 回调测试使用 6 API、6 Inbox、4 异步 AI worker；正常对话额外使用 2 个真实 Agent、同一配额 SQLite、本地固定 3s 模型响应和 0.2s 播放确认。
- 负载夹具没有运行 PBX、12 个媒体进程或后台通用任务 worker；会话从 500 个合成 IN_AI 状态开始。预约/静音等通用任务链另由回归测试覆盖，不能把本次对话夹具当作完整外呼容量。
- 回调门槛保持网关逐事件投递与 Inbox 提交完成各自不超过 1s；二者最大值不能直接相加当同一个事件的端到端延迟。
- 正式回复的模拟控制门槛是 P99 ≤ 4.2s（3s 模型 + 0.2s 播放确认 + 1s 控制预算），不等于终句到客户首音。ASR、TTS、SIP/RTP 和客户侧声音未被此模拟器验证。
- 混合回调场景为每秒 200 次终句 + 400 次媒体事件；每通话约 2.5s 一个终句，比 3s 模型响应更快，主要覆盖过期轮次保护，不用于证明每秒 200 次有效回复。
- 正常对话场景覆盖每会话 6.25s / 10s 一轮，目标总计 80 / 50 轮/秒。早期集中起步为 200 个首次终句/秒，最终场景按各自目标速率均匀起步。客户等待正式回复后再进入下一轮；若系统变慢，实际吞吐会下降，不能只看计划发送率。
- 候选完整配置静态汇总为 CPU 限额 31.5 核、内存限额 52.75GiB、应用 DB 连接 64、客户在途 500、媒体资源槽位 600、AI 槽位 640；这是资源预算检查。对话夹具仅配置 56 个应用 DB 连接预算，另有观察器 5 个，未运行的通用任务 worker 对应完整配置中额外 8 个连接。

## 已知问题与后续修复顺序

1. 500 会话相关测试已有通过轮次，但重复、延长或突发负载仍可能超过门槛。最终结果表中的失败保留；不能将短轮通过推广为稳定容量。
2. AI 工作池存在排队，当前播放等待仍占用动作线程。下一步优先将播放网络等待与 ORM 提交拆为有界异步阶段，并保留 call/attempt/turn 校验、租约和迟到结果拦截；继续加线程的对照无收益。
3. 长回调测试出现 PostgreSQL WAL checkpoint 和锁等待。此次负载库使用开发默认 128MB shared_buffers / 1GB max_wal_size，候选配置为 2GB / 4GB；不能据此判定目标主机上限。需要在目标配置下采集锁等待、查询计划、checkpoint、磁盘 fsync 和 CPU 节流，验证优化与故障余量。
4. 对话测试观察器已从历史全表轮询改为未完成轮次的时间窗口查询，避免历史增长放大观察开销。测试器与服务仍同机，无法消除测量干扰；最终对照采用修正后的观察器。
5. 原压测项目积累导致 Docker 网络地址池耗尽，主机可用磁盘一度约 11GiB。已清理本轮临时项目；新增带存在性保护、超时清理和报告保留的执行入口，避免后续继续积累。该启动中止不记为应用容量失败。

## 正式上线前置条件

1. 在目标 Linux 32 核 / 64GB 上重建并固定全部服务镜像，核对 CPU 节流、内存、连接池、磁盘 fsync、网络和真实依赖；将发压器放在另一台主机。
2. 按原架构方案补全 PBX、12 媒体进程、通用任务 worker、录音上传和云 ASR/TTS/LLM；核验供应商并发/RPM/TPM/CPS 与真实线路额度。
3. 按 20 → 50 → 100 → 200 → 350 → 500 逐档验证，覆盖 500 全接通 AI、均匀对话、集中终句、集中挂断、打断与转人工；失败不得因队列最终清空而记为通过。
4. 通过真实声音、录音、故障恢复与对账；500 档 8 小时、混合负载 24 小时。单机仍有整机故障域，不等于高可用。
