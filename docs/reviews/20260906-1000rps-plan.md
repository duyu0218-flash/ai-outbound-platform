# 持续成功处理 1000 RPS：当前证据与实施顺序

当前未达标。这里的目标固定为有效的通话状态回调：验签、事件去重、通话状态处理与可靠任务入队成功，并且下游能够持续消费。接口准入拒绝不计为成功，收到请求也不等于完成业务。1000 RPS 与 1000 路 AI 同时通话是不同容量指标。

本轮改造已解决主要请求准入与回调线程/连接归属问题；下一阶段需要降低单请求成本，再验证进程扩展。最终冻结代码在 1000 RPS 短测中的成功吞吐为 217.63 RPS，200 RPS 长时观察仅 154.30 RPS 且存在发压漏发和采样空档；两者均未通过容量验收。详见 [接续验收数据](20260906-request-concurrency-resume.md)。不能据此承诺采购容量。

| 已测证据 | 对优化的含义 |
|---|---|
| 100 次合成终态回调剖析，每次执行 28 条 SQL | 当前路径在 1000 RPS 下约产生 28000 条 SQL/秒，还需承担提交和连接协议往返；不能只调大入口限额 |
| 其中 5 次 SAVEPOINT、5 次 RELEASE SAVEPOINT | 合并事务内提交、减少保存点往返值得优先实验；仍需在去重竞争失败时正确回滚 |
| 同一个 CallSession 有多次按主键查询；提交会使 ORM 对象过期 | 减少不必要的 refresh 和重复加载，必须保留并发状态、轮次和权限校验 |
| 同步 analyze_call 在样本中约占 3.94 ms/事件 | 将分析转为持久化后台任务；不可只调用不可靠的进程内后台函数 |
| 剖析平均路由 19.73 ms，其中游标执行累计约 11.11 ms | 该样本包含剖析开销、同步顺序执行且与本机稳态测试并行，不是生产延迟或容量上限 |
| 大库主键/分析查询执行计划使用索引，单次数据库执行约 0.02—0.09 ms；空交接表扫描约 0.003 ms | 现有证据更支持优先减少往返与 ORM/请求处理开销，不能因为看到 Seq Scan 就盲目加索引 |
| 压测采样中两个 API 进程 CPU 接近单核饱和，AnyIO 线程等待为 0；早期连接未满，长时运行中每进程借出连接峰值达到 10 | 同时测每请求 CPU 成本与持有连接时长，再测试多进程扩展；扩大连接池本身不能减少这些成本 |

原始数据位于 `artifacts/concurrency-resume-20260906/callback-profile.json`、`callback-profile.txt`、`query-plans.json` 和 `runtime-samples.jsonl`。SQL 剖析与执行计划应结合看；参见 [SQLAlchemy 性能诊断](https://docs.sqlalchemy.org/en/20/faq/performance.html) 与 [PostgreSQL 16 EXPLAIN](https://www.postgresql.org/docs/16/using-explain.html)。

另做了事务合并候选实验：在同一主机负载下交替运行 200 个基线事件与 200 个候选事件，SQL 从 28 条/事件降到 17 条/事件，平均耗时从 54.70 ms 降到 36.09 ms，约减少 34%。这不能换算成已实现的 API 吞吐。随后专项测试发现：其他事务在先查后插的间隙写入相同 Outbox 幂等键时，候选的回滚会擦掉此前的通话终态和事件；现有实现的同一对照测试通过。因此候选已排除，未修改应用中的事务实现。后续减少保存点必须先把预期唯一键冲突限制在局部事务内，或采用经过并发验证的 upsert。候选只存在于 `artifacts/concurrency-resume-20260906/profile_paired.py` 等实验脚本中。原始性能结果为 `profile-paired.json`，正确性对照为 `candidate-regression.log`、`baseline-conflict.log` 和 `test_candidate_conflict.py`。

实施顺序：

1. **优化现有事务，保持接口语义。** 回调验签后，在同一事务中处理去重、关键通话状态和 Outbox。去掉无业务必要的提交后重查，合并状态字段更新。试验将热路径降到约 6—10 条 SQL/事件；这只是工程目标，尚未实现或证明可达。每次减少一次查询都必须有相应的重复事件、并发、旧轮次和终态保护回归。
2. **持久化异步分析。** 为通话分析增加独立任务类型、稳定幂等键和原始拨号轮次。后台任务受领取租约及超时约束；旧轮次结果不能覆盖新一轮通话。关键终态、坐席释放及限额仍按业务一致性要求及时落库。前端需要明确显示分析处理中、完成或失败，不能先返回虚假完整结果。
3. **减少去重和入队往返。** 在 PostgreSQL 中评估唯一约束配合 `INSERT ... ON CONFLICT ... RETURNING`，取代可合并的先查再插及重复刷新。保留 SQLite 的开发测试实现，验证并发重复不会回滚其他业务变更，也不会确认丢失事件。
4. **分离并测量消费能力。** 单独测分析、客户回调、录音和 AI worker。1000 个入口事件/秒未必生成 1000 个相同任务/秒，应按真实事件配比测量。平均消费能力必须覆盖实际任务生成速率，队列最老年龄不能持续增加；不能只证明入口能够不断堆积任务。
5. **按资源预算测试进程扩展。** 先记录单进程 RPS/CPU、数据库事务率和内存，再测 2/4/6 等进程配置。连接总预算包含所有 API、worker 和运维连接。发压器与被测服务应放在不同资源环境。当前是本机 Python 3.12 双进程，数据库位于 Docker；Docker 可用 12 CPU、约 7.75 GiB 内存，这不是候选生产规格。生产硬件、进程数、连接池大小须由扩展曲线确定，不能按现有结果线性承诺。
6. **在冻结的候选环境验收。** 按 200/400/600/800/1000 RPS 到达率逐级测试；1000 RPS 稳态至少 30 分钟，并补高峰持续负载、数据库/Redis 中断和恢复、进程重启、大库与资源限制场景。上线前按业务风险延长至数小时或一天，并完成灰度/回滚。

建议先固定的验收口径：

| 指标 | 候选验收要求 |
|---|---|
| 发压有效性 | 实际到达 1000 RPS；发压器未发送/丢弃/积压单列，不补发成一条更长的低速曲线 |
| 接口成功 | 200/202 等约定成功响应必须对应可靠落库；约定成功语义后才计数。429/503/504、连接错误与重试放大分别记录 |
| 稳态延迟 | 先以 P95 ≤ 200 ms、P99 ≤ 500 ms 作为候选目标；这些是待业务确认的目标，当前未证明达到 |
| 正确性 | 同一事件最终只产生一份约定业务效果；发压器导出逐事件结果以核对 HTTP 超时后的提交，重试复用事件标识。本轮只有聚合差额，逐事件对应尚未验证 |
| 下游闭环 | 稳态任务队列不持续增长，任务最老年龄有上限；按消费者最终完成量核对输入事件 |
| 过载与恢复 | 超预算有界拒绝，降低负载或恢复依赖后自动恢复；连接和线程回落，无终态倒退、重复实际拨号或短信 |

最终交付必须同时有入口、数据库和消费者三层证据。只有这三层在目标负载下全部达标，才可以说“持续成功处理 1000 RPS”。真实 1000 路电话还需要另外验证网关/PBX、ASR/TTS/LLM、线路配额、录音与实际声音。
