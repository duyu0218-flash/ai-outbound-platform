# 外呼平台功能缺陷审查（2026-09-05）

审查对象：当前本地分支 `fix/review-state-and-session-isolation`，提交 `7ed302b59d81db6452df1c8afe98dfb596597dd0`。实际仓库为 `duyu0218-flash/ai-outbound-platform`，开始审查时工作区干净。未刷新远端；本文不代表远端、CI、容器或生产状态。

结论：确认 7 项功能缺陷，其中 P1 三项、P2 四项。六项通过隔离数据库的接口/服务场景复现；客户选择范围问题通过前端源码与分页接口结果交叉确认。优先修复转人工状态和任务配置一致性。

## 1. [P1] 接听转人工的迟到响应覆盖挂断或已接通状态

位置：`backend/app/api/routers/voice_operations.py:424-436`。

触发：调用 `/calls/{id}/handoffs/{handoff_id}/accept`，网关转接 HTTP 响应返回之前，先收到 `completed` 或 `human_connected` 回调。

实测：回调已把通话写为 `completed`，随后 accept 接口返回 200，把它重新写成 `handoff_transferring`，交接从终结状态改回 `accepted`，并保留非空 `finished_at`。另一用例中，已接通的 `in_human` 同样倒退成 `handoff_transferring`。

影响：已结束通话重新占用活跃容量，页面状态错误，坐席保持忙碌。真实网关回调与命令响应到达顺序不固定。

建议：在发送转接前原子绑定当前轮次、通话及交接状态；响应返回后按轮次和允许的前置状态做条件更新，保留期间已经发生的接通、未接听和终态回调。

## 2. [P1] 手动转人工在坐席未接听时无法重新入队

位置：`backend/app/services/call_service.py:851-866`；配套回调条件为 `backend/app/api/routers/webhooks.py:203-219`。

触发：坐席通过 `/calls/{id}/handover` 发起手动转接，网关接受命令后，坐席未接听并回传 `human_unavailable`。

实测：handover 返回 200 后，通话是 `waiting_human`，坐席为 `busy`，未创建 HandoffRequest。未接听回调返回 `ignored / inactive_handoff`。

原因：手动转接在命令返回时把 `handoff_transferring` 改成 `waiting_human`；未接听回调则要求前者，并要求存在 accepting/accepted 交接记录。两个入口的状态约定不一致。FreeSWITCH 网关代码实际会发送该事件。

影响：客户无法通过等待队列重新分配，坐席无法被自动恢复为可接听，直至其他清理或人工干预。

建议：手动和 AI 转人工共用交接生命周期，记录交接对象，等待真实坐席结果后再决定接通、回队和释放坐席。

## 3. [P1] 停止任务修改后，重启仍沿用旧通话配置

位置：`backend/app/services/call_service.py:1282-1294`。

触发：创建并准备任务 → 停止 → 修改模式及重试次数 → 再次启动。同一客户的未拨通话会被复用，但配置不随任务更新。

实测：任务已成功保存为 `human_only`、重试次数 5；重启后的通话仍为 `ai_only`，`max_attempts=2`，而新配置应对应 6 次总尝试。此场景尚未发出任何实际拨号，不涉及修改历史已拨记录的争议。

影响：界面回显与实际执行方式不一致。该复用路径也不更新已绑定的流程版本；此次动态用例只验证了模式和重试次数。

建议：对未实际拨出的旧记录重建或同步执行配置；已拨记录保留历史快照，并明确编辑后剩余任务的生效规则。

## 4. [P2] 坐席通话列表先分页后过滤，漏掉本人通话

位置：`backend/app/api/routers/calls.py:105-114`；底层分页在 `backend/app/services/call_service.py:611-625`。

触发：同租户其他通话比该坐席的通话更新。

实测：插入一条该坐席通话及 20 条较新的其他通话；坐席请求 `page=1&size=20` 返回空数组，`page=2` 才返回本人通话。

影响：坐席工作台固定请求第一页 20 条，可能显示没有通话。通话记录页固定抓取第一页 100 条后在浏览器分页，也无法访问服务器后续页。

建议：把普通坐席的 `human_agent_id` 条件加入 SQL 查询后再分页，同时让前端分页与后端页码联动。

## 5. [P2] 任务客户选择器只能选择第一页 200 人

位置：`frontend/src/pages.tsx:819`、`:885`。

前端固定请求 `/api/v1/contacts?page=1&size=200`，下拉搜索只筛选这批本地 options，没有后续分页或服务端关键词搜索。

接口实测：202 个联系人中首批只返回 200 个，其余 2 个在第二页。源码确认这些后续客户不会进入任务表单的候选项。

影响：批量导入名单后无法通过该页面选择整批客户或搜索后续客户。这是界面限制，不是后端任务接口最多只能绑定 200 人。

建议：支持服务端搜索和分页选择；批量外呼宜增加按客户分组、筛选结果或导入批次选择，并显示实际选中人数。

证据边界：未启动浏览器操作该下拉框，结论来自源码与真实本地分页接口结果。

## 6. [P2] 暂停期间通话全部结束，恢复后任务一直显示运行中

位置：`backend/app/api/routers/campaigns.py:448-453`；完成判定在 `backend/app/services/call_service.py:501-507`。

触发：任务暂停期间最后一通电话结束，随后点击恢复。

实测：唯一通话已 `completed`；resume 返回 200 并设置 `running`。执行调度器的待拨和重试扫描后，任务仍为 `running`，没有任何可执行通话。

原因：结束回调只对 running 任务做完成判定；恢复无条件设置 running；后续没有待处理通话时，调度扫描不会再触发该任务完成判定。

建议：恢复事务内检查剩余待拨、活动和重试记录；无剩余工作时直接完成，或在恢复后立即调用统一完成判定。

## 7. [P2] 重试次数不能设为 0，无法配置每人只拨一次

位置：`backend/app/schemas.py:167`、`frontend/src/pages.tsx:889`。

实测：`retry_limit=0` 创建任务返回 HTTP 400（本项目验证错误经中间件转换）。后端约束与前端 InputNumber 都要求最小 1，执行层却按 `retry_limit + 1` 计算总尝试数。

影响：任务只能允许至少一次额外重拨，无法配置“无人接听也不自动重拨”；额外重拨仍受其他合规及额度策略约束，并非所有失败都会必然重拨。

建议：前后端统一允许 0，0 次重试对应一次初始拨号。
