# 回调吞吐定位、修复与下一步

后续状态：本记录提出的 Inbox 持久接收与有界批处理现已实现，见[修复及验收报告](20260908-callback-inbox.md)。以下保留此前阶段的结论，容量通过与否以新报告为准。

基线提交：`667b4c9`。日期：2026-09-08。

**本轮修复了重复数据库读取和 AI 写回与回调之间的锁顺序问题，并建立了 Linux 同机隔离压测。事件完整处理已有通过记录，但 600 回调/秒、最大排队不超过 1 秒的容量目标仍未通过。** 不能把最终清空队列称为持续吞吐达标，也不能把本轮结果称为 500 路真实电话容量。

## 找到了什么，改了什么

1. **启动阶段的拒绝被误混入稳态吞吐。** 上次 793 次 503 中，789 次集中在一个 API；旧夹具只等代理返回一次健康就开始发压，其他 API 仍可能在启动。本轮逐一等待六个 API 就绪。修复后的完整 macOS 代理实验没有 HTTP 错误，但仍积压，说明启动问题不是唯一瓶颈。
2. **回调事务重复读取。** 服务方法在一个外层事务内多次释放保存点，默认 ORM 属性过期导致同一已锁定通话被重复 SELECT。本轮仅在请求专用 `WebhookSession` 内保留对象属性；其他普通会话维持原行为。语音/媒体入口合并读取与行锁，跳过不必要的 refresh，媒体计时器复用同一事务内已经锁定的状态。保存点、外层事务、去重与 Outbox 原子性保留。
3. **真实 PostgreSQL 死锁。** AI 结果写回先锁 conversation/realtime，再插入带通话外键的 metric；回调先锁 call，再更新 conversation/realtime，形成环路。AI 结果写回、动作开始、TTS 返回写回及提交后更新计时器前，统一先锁 call、核对 attempt/turn，再操作子状态；模型/电话网络等待前仍先提交释放连接。新增真实 PostgreSQL 阻塞测试，确认持有 call 锁时 AI 不会先占 conversation 锁。
4. **测试网络和存储开销。** Docker NGINX 往返 macOS 的路径中，API 内部平均约 16–24 ms，而端到端 HTTP P99 约 651 ms。改为同一 Linux 回环网络后明显缩短。SQLite 放在 macOS 挂载目录时，批提交 P50 约 30 ms；改用 Linux 数据卷后约 9 ms。新测试 Compose 不发布端口，全部使用合成模型/号码和独立数据库。
5. **校验口径补齐。** 最终转写只统计客户终句，AI 等待提示另计；增加媒体去重数、通话终态、失败指标和 AI 执行次数检查。只要正确性或容量 SLO 有一项失败，工具现在返回非零退出码。接口 200、队列清空和容量达标分别记录。

对比同一种 macOS 代理路径的两次实验，每个成功回调的平均 SQL 数从约 22.85 降至 17.10。该数包含冷启动及业务分布影响，是观测值，不是对每一种事件的固定 SQL 上限。连接池几乎没有 checkout 等待，当前证据不支持直接扩大 DB 连接池。

## 同负载结果

每次均为 500 个合成通话、30 秒内计划发出 6,000 个终句和 12,000 个媒体事件，即 600 回调/秒；模型响应延迟设为 3 秒。完整回调须在数据库提交后才返回 200，SQLite 保持 WAL + FULL。600 个事件/秒不是 600 路电话，也不是实测音频带宽。

最后一项处理结束约 56.22 秒：客户终句 6,000，媒体去重记录 12,000，AI 任务 6,000 完成，最大执行次数 1，失败指标 0，500 个通话仍为 IN_AI。部分旧轮次输出被新轮次保护丢弃，这是既有设计；不能要求 3 秒模型在每通话 2.5 秒一个新终句时产生 6,000 次有效播报。未出现失败不表示处理速度达标。

原始结果位于[上一轮证据目录](evidence/20260908-single-host-500/)的 `dialogue-profile-results.json`、`dialogue-final-proxy-results.json`、`dialogue-linux-results.json`、`dialogue-linux-volume-results.json`。分进程 SQL/CPU/等待汇总见[本轮证据目录](evidence/20260908-callback-throughput/)的 `api-stage-summary.json`。

保留了两个中间诊断：`dialogue-direct-results.json` 是减少读取后绕过代理的直连实验，复现了死锁；`dialogue-locked-results.json` 是第一批锁修复后的实验，仍有提交后计时器路径的锁问题，后续已补齐。两者旧版校验把 AI 提示计入全部转写，不能把该计数当作客户事件丢失证据。

另试过保留 SQLite WAL 连接，结果批提交耗时仍约 9 ms，没有收益，已撤回该实现。其 `dialogue-linux-wal-results.json` 留作失败证据：1 次 503、1 个 AI ReadError 引起兜底终止，容量与正确性均失败；不将它作为最终实现的通过记录。

## 下一步应怎样解决

下一项代码工作应将**每条回调的同步业务处理改为持久化接收和有界批处理**，而不是继续单纯扩大超时或队列。该改造尚未实现：

- 入口完成签名、大小、事件标识校验，把事件写入持久化 Inbox 并提交后 ACK；禁止先 ACK 后仅写内存或只发 Redis 消息。
- 消费者按 call_id 分区，使用数据库租约保证一个通话同时只有一个消费者。同一通话的语音、媒体、终态保序，继续检查 attempt/sequence。重启和重试复用同一个事件标识。
- 每批先按稳定次序锁通话，批量写入事件/指标；业务变更、Inbox 完成标记和后续 Outbox 在同一事务提交。先试 16–64 条、约 5 ms 的批窗口，再按实测收敛，不能提前承诺这个参数会达标。
- 回压依据端到端未处理事件年龄和总积压，超限停止新拨号；Inbox 接收快但业务消费慢时，readiness 不能继续报可接新呼叫。
- 用相同 600 回调/秒负载复测：实际发出无漏发、零非预期错误、持续不积压、最大排队不超过 1 秒、无丢失/重复业务动作；再补突发、消费者崩溃、重放、死锁及长稳测试。

该项改造的目的，是合并每条事件当前约 17–19 条 SQL 带来的事务/调度成本，减少回调等待业务处理占用 HTTP 槽位的时间。**只把等待移到 Inbox 而不提升消费速度，不算解决。** 同时需要在评估的目标 Linux 主机、Linux 本地持久化盘上复测；本次 Docker VM 仅 12 vCPU、约 7.75 GiB，与候选 32 专用 vCPU/64 GiB 不同，当前结果不能证明换服务器必然通过。
