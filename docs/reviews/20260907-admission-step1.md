# 回调短队列落地与多进程压测

日期：2026-09-07。基线 `941e3d1`。目标：落地第一阶段的短时间有界等待，保持数据库连接预算，验证实际多 API 进程的 HTTP 回调行为。

## 改动与生效范围

- `deploy/compact/backend.env.example` 将每进程等待上限从 0 改为 8，最长等待为 0.05 秒。
- `docker-compose.compact.yml` 在 control-api 显式设置上述两个参数，避免旧 env 文件仍为 0 导致部署未生效。该 Compose 环境配置优先于 env_file；回滚也需修改 Compose。
- 保持每进程回调处理 4、普通业务处理 2、总处理 6、数据库连接池 6、overflow 0，以及每台 2 个 API 进程。四台 API 加 worker 的原连接预算仍为 72，不增加服务器。
- 等待发生在认证和数据库处理之前；排队期间不进入业务处理函数。等待数超过 8 或超过 50ms 返回带 `Retry-After` 的 503。操作系统调度可能使实际返回时间超过 50ms；完整请求耗时还包括认证、业务事务和网络。
- 保留现有请求超时后实际执行结束才释放名额、取消等待时释放等待名额的机制。该队列按进程计数、由请求类别共享，尚非分类 FIFO；不承诺消除持续过载。
- 使用现有中间件能力，本轮没有扩大数据库连接池或重写业务事务。新增回归验证 4 个执行中加 8 个等待、第 13 个拒绝、释放后完成，以及等待超时不执行、名额恢复。

## 涉及入口和状态

| 入口 | 状态和验证 |
|---|---|
| status Webhook | 接纳、短等待、满队列拒绝、等待超时、原事件重试、重复事件 |
| 登录、退出、角色入口 | 登录/失败、退出、后台与坐席隔离、返回 |
| 客户、任务、话单、设置 | 搜索和分页、创建/编辑/保存回显、启动/暂停/恢复/停止、话单及事件 |
| 页面和静态资源 | 多资源并行加载、受限参数下页面完整显示 |
| Mock 外呼与人工接管 | 外呼、转接无人接听重入队、接管、挂断 |

本项目业务链路为登录 → 客户 → 外呼任务 → Mock 外呼/转人工 → 话单及事件 → 设置 → 退出；购物车、下单、支付不适用于该项目。

## 测试环境与方法

本机 macOS，独立 PostgreSQL 16、Redis 7 容器；真实 HTTP、HMAC 验签、Redis 限速和 PostgreSQL 事务。每个样本都是独立、已存在的合成话单，发送 completed 状态；开启异步终态分析，仅持久入队，不并行运行消费者。避免前端构建、浏览器及后台回归与压测同时运行。

比较同一代码的单/双 Uvicorn API 进程，等待 0/8、超时 50ms，其余预算一致。测试专用 ASGI 包装器添加 PID 响应头和每 200ms 运行时采样，不进入交付应用。按 PID 核验实际请求分布；采样数据库连接/锁等待、进程 CPU/RSS、准入等待和拒绝、连接池等待/失败。瞬时峰值可能被 200ms 采样遗漏。

发压器有固定到达节奏，报告成功、503、漏发及发压排队；p95/p99 使用从计划发送到响应完成的完整时间。先测 4 个独立长连接池，再补测 20 个连接池，所有首轮结果均保留，不将挑选的最佳样本作为保证。客户端上限 100/500 是发压参数，不是实际同时请求数或电话路数。

每轮首发后核对话单终态、Webhook 去重凭据和分析任务；非成功请求以原事件 ID 重试，另重放 20 条已成功事件，再核对恰好一份终态/凭据/分析任务。重试不合并进首次成功率。任务积压是本次关闭消费者的预期结果，不能据此认定业务全链路吞吐达标。

**验收结论：短队列配置和正确性通过；100 RPS 始终零拒绝的容量门槛未通过。** 两轮单进程 100 RPS 短测启用等待后均全成功；双进程 100 RPS 两轮 120 秒测试分别是 12000/12000 和 11990/12000。后者 10 次 503 是约 0.083% 的首次失败率，不能以另一轮全成功掩盖。双进程 200 RPS 两轮分别有 138 和 37 次拒绝，未继续向更高负载升压。

- 首轮双进程短测有 2987/13 的进程分布；补测 20 个连接池时仍出现 2850/150，增加客户端连接数并不能保证均衡。在 200 RPS 补测中分布已接近 3002/2998，仍有 37 次等待超时，说明还存在处理尾延迟问题。
- 两个 200 RPS 样本：前者 135 次等待超时、3 次满队列拒绝；后者 37 次等待超时。前者热点进程平均约占 1 个 CPU 核；后者两个进程平均约占 0.735 和 0.774 核（含本次探针和收尾）。这是进一步剖析 CPU/请求耗时的依据，不能直接归因为数据库连接不足。
- 各轮没有发压漏发，响应类别仅 200/503，无 HTTP 请求超时。所有进程的连接池借用超时计数为 0；200ms 采样未观察到数据库锁等待，结束后借出连接归零。采样未见不代表从未发生瞬时等待。
- 最终独立 SQL 核对：60000 条 COMPLETED 话单、60000 条 Webhook 凭据、60000 条分析任务；共 246 次失败请求按原事件 ID 重试成功，另做 240 次成功事件重放，没有新增重复任务或凭据。分析任务是 PENDING，因为本次特意关闭消费者；这里验证的是入队正确性，不是后台任务处理速度。
- PostgreSQL/Redis 后端全量 185 项通过；双 API 进程、等待 8/50ms 下 Chromium 14 项通过；Python 编译、Git 差异检查及 Compose 生效参数检查通过。
- 浏览器使用单独 Mock 数据库、规则 Agent、内联任务执行，并仅将隔离租户设为全天测试；压测使用另一数据库、关闭内联执行。没有修改业务实例的外呼时段策略。前端源码未改，本轮没有重复前端构建。

完整数值及源代码/原始证据 SHA256 见[证据 JSON](evidence/20260907-admission-step1.json)。本机原始样本、PID/数据库采样、发压/重试脚本、浏览器日志位于 `artifacts/admission-step1/`。4/20 连接池分别来自有界发压器 100/500 的客户端上限；实际峰值另见证据，不表示 100/500 个同时请求。

## 验证边界与上线条件

短队列只能吸收突发，实际目标负载下出现的 503 仍计为失败。长连接可能集中到少数 API 进程，应检查负载均衡上游连接分布；不能用两个进程的理论名额相加来推算稳定 RPS。

本机双进程不等同于四台服务器、八 API 进程，也没有施加部署模板的 2 vCPU/2GiB 容器限额。完整部署、托管数据库网络时延、后台消费者与媒体同时运行、单机失效与恢复仍需验证。真实 200/500 路、模型配额、音频质量、坐席真机和生产发布不属于本次已验证结果。


## 后续动作与交付状态

1. 在正式四节点入口检查每节点、每 API 进程的请求分布及长连接复用，不以客户端连接数量推定分流效果。
2. 对同一 100/200 RPS 负载记录完整请求分段耗时及 CPU 热点，区分准入等待、认证/Redis、业务 SQL 和响应开销；定位尾延迟后再决定是否进入每进程 8 回调、10 连接的第二阶段。此次保持第一阶段参数，没有靠继续加大等待上限来获得更漂亮的成功率。
3. 预生产需在部署资源限额、托管服务真实网络、后台任务及媒体同时运行时复测，并做四台八进程和少一台故障场景。正式上线前依然需要真实 200/500 路验收。
