## 门槛与负载口径

- 对话执行生产 Agent 和 HTTP 模型客户端，但云模型固定模拟等待 3 秒，播放确认固定模拟等待 0.2 秒，不产生真实语音。回复 P99 预算为 4.2 秒；每轮还必须在下一轮计划时间前完成。
- 50 / 80 / 100 / 125 档每个会话轮间隔分别为 10 / 6.25 / 5 / 4 秒；错过截止分别为 0 / 743 / 972 / 2285 轮。
- 绝对排程记录了每 10 秒计划、发出、完成数量。客户等待上一轮回复会使高档位落后于计划；125 档前 20 秒计划 2500 次，实际仅发出 2196 次，其余 304 次随后发出，不能声称持续达到 125 轮/秒。
- 回调投递最长等待、Inbox 最长完成延迟等需不超过 1 秒，且无错误或遗漏。600 和 1200 档均未达到门槛。
- 高档位短轮 P99 不单调，运行时长、排程落后和同机负载不同。没有重复试验与置信区间，不能用单轮结果排列各档稳定容量。

## 已定位的限制

1. 80 档 AI 数据库工作池阶段排队 P99 约 0.75–1.21 秒，阶段执行 P99 多为几十毫秒，模拟播放确认 P99 约 237ms。证据显示工作池排队仍是主要延迟来源。下一步应分析每轮重复短事务和查询，以及领取、续租对业务提交的竞争，再做固定负载对照。
2. 600 档发压 P99 滞后约 4ms，投递最大 297ms，超标发生在 Inbox 完成环节。PostgreSQL 出现 WAL checkpoint，但没有充分的连续锁等待和磁盘采样确认唯一根因；checkpoint 日志持续时长不等于业务停顿时间。
3. 1200 档在投递队列侧出现明显积压。需分别复验投递批量、接收限流和 Inbox 消费，保留同通话顺序及提交原子性。
4. 健康文件阶段统计为最近最多 2048 个样本，不能代替全程指标。原负载 JSON 的 `ai_action_threads_per_worker=8` 是旧静态描述；本轮实际健康文件显示 `action_threads=0`，异步网络阶段不使用旧动作线程。
