# 回调持久接收与有界批处理修复

## 改造范围

六个电话回调入口（status、transcript、speech、dtmf、media、recording）在启用 `CALLBACK_INBOX_ENABLED=true` 后，先校验签名和请求模型，持久提交 Inbox，再返回 HTTP 200。返回值 `result=received`、`receipt_id`、`processing` 明确表示接收状态；通话状态、转人工结果和话单需从业务接口读取。SMS 回执仍使用原同步事务路径。

接收端使用 64 个固定分区，同一 call 始终落在同一分区。分区行锁覆盖接收事务，保证序号与提交顺序一致。消费者用 PostgreSQL 事务 advisory lock 独占分区，按接收序号处理连续事件。业务提交改为 flush，每条事件一个保存点，每批最多 32 条、事件之间检查 50ms 时间预算，整个批次一次持久提交。数据库语句上限 2 秒、锁等待上限 200ms；时间预算不会中断执行到一半的业务事件。

业务状态、去重标记、Inbox 完成状态和 TaskOutbox 在同一外层事务中提交。进程退出/被杀、SQL 或提交失败会回滚批次；重复业务插入只回滚当前事件保存点。打断播放也写入 Outbox，并携带 attempt、播放标识、轮次和语音事件代次，旧任务不能停止新一轮播放。

默认每分区最多 256 条待处理事件、4MiB 原始正文，单条正文最多 256KiB；默认总上限 16,384 条/256MiB。满分区返回 503，原身份的重复接收仍可确认；同身份换正文返回 409。处理成功后清空正文、保留摘要去重 7 天；超过回放窗口的旧事件仍由现有业务去重保护。待处理/死信不自动删除。

失败指数退避，5 次失败进入死信，阻止同一通话后续事件越序；同分区其他通话继续。修复原因后通过 `python -m app.callback_inbox_worker --retry <receipt_id>` 重排死信，无跳过事件功能。

## 启用与回退

1. 先停止新拨号，暂停回调入口的流量切换，允许网关持久账本保留重试；备份数据库。
2. 执行 `backend/migrations/postgresql/20260908_callback_inbox.sql`，保持生产 `AUTO_MIGRATE=false`。
3. 单机模板所有后端角色启用相同模式，启动六个 `app.callback_inbox_worker`；确认消费者心跳、无死信与积压，再放行 API 和调度。禁止混用同步与 Inbox 接收进程。
4. `/readyz` 和拨号准入同时检查消费者心跳、死信及最老待处理年龄（默认 1 秒）；既有回调继续接收以完成在途通话。`/metrics` 提供 Inbox 数量/字节/年龄/死信/存活消费者/累计消费量/最大消费延迟。`/metrics/runtime` 保持数据库独立。
5. 回退必须先暂停入口、排空 Inbox（包括修复死信）再统一停用；有未处理事件时启动同步模式会失败。进程优雅退出提交当前批次，强制退出则由数据库回滚，其他消费者自动接续。

数据库连接预算保持 64：六个 API 各 5（回调 4、管理 1），六个串行消费者各 1，四个 AI worker 各 5，后台 worker 8。没有扩大总连接数或延迟验收门槛。

### 容量验收与已知问题

同口径负载仍为 500 条合成通话、30 秒内 6,000 个终句和 12,000 个媒体回调，六个 API、六个 Inbox 消费者、四个 AI worker，模型模拟等待 3 秒。最终第 6 轮源码 SHA-256 与交付实现一致：18,000 条均持久接收并完成消费、Inbox 死信/剩余均为 0；有 16 次接收端 503 重试，Inbox 最大消费延迟 1.172 秒、网关最老排队 32.876 秒、HTTP P99 236.62ms；2 次模型请求 ReadError 触发失败兜底，498 条保持 IN_AI、2 条完成。因此该轮业务正确性和容量 SLO 均未通过，**当前仍不能宣称 500 路商用达标**。原始结果见 `dialogue-inbox-06-results.json`，有界队列与准入阈值未放宽。

前五轮失败记录完整保留：第 3 轮业务正确性通过，但 2 次 503、Inbox 最大消费延迟约 1.28 秒；第 5 轮 18,000 次接收均为 200，但 Inbox 最大消费延迟约 1.40 秒、网关最老排队约 41.50 秒，并有模型请求 ReadError/失败兜底。它们都不满足小于 1 秒、无业务失败的容量门槛。

观测显示，接收 SQL 从原同步业务约 17–19 条降至正常路径 1 条 PostgreSQL 原子 SQL；网关批持久写入第 5 轮 P50 约 13.65ms，累计约 39.99 秒。此数据提示网关账本持久提交/本机资源仍需继续定位，不能仅凭接收端变快断言整链路瓶颈消失。没有放宽超时、队列上限或验收门槛。

正式生产、真实线路、真实云 ASR/TTS/LLM、目标 32 核/64GiB Linux 主机、500 路真实音频与长稳测试均未验证。本机 Docker VM 为约 12 vCPU/7.75GiB，合成回调测试不能替代目标服务器的商用容量验收。
