# 2026-09-16 数据库工作池优化与验收

## 结论

已减少 AI 热路径重复 ORM 查询，保留状态、attempt、turn sequence、租约及行锁约束。相同固定样本、相同资源和观测条件下，80 档优化前两次回复 P99 均超过 4.2 秒；优化后五次均低于 4.2 秒且正确性通过。此处“80 档”指初始 speech start / final transcript 计划速率 80/s，不能表述为 80 路真实语音或生产容量。

600 事件/秒回调仍有长尾超标；本轮没有完成所有六档性能验收，也没有生产发布。

## 修改范围

- dispatcher / ai_actions：一次带 populate_existing 的查询完成加载与状态刷新；需要写入时保留 FOR UPDATE。以 no_autoflush 防止旧缓存状态先写回。保留后续状态重检、事务和锁顺序。
- async_ai：增加默认关闭的确定性抽样，记录任务/通话 ID、排队、执行、SQL 和提交计数。每进程最多保留最近 512 条；不收集电话号码、文本、SQL 正文或租约令牌。
- callback_inbox：补充收据等待、业务执行及批次提交耗时；只在成功提交后保存抽样，不改变回执事务与顺序。
- 数据库观察：失败 SQL 也计入耗时/错误数量，记录 PostgreSQL 阻塞会话和 cgroup 限额。压测两组均启用相同的 1/16 抽样及每 2 秒只读采集。

## 已知问题、环境限制和上线前置条件

1. 600 事件/秒仍未达到 1 秒 Inbox 门槛；100/125 对话档和 1200 回调档本轮未复验，不继承为已通过。
2. Docker Desktop 12 CPU、约 7.75 GiB 内存，发压与服务同机。cgroup 数据来自发压容器，不能代表全部业务容器或宿主机；采样没有看到该容器 throttling，不能据此排除 CPU 竞争。
3. 600 档数据库采样看到 WALSync、WALWrite、advisory 和 transactionid 等等待，最多 3 个阻塞会话；仅凭这些采样不能确定哪个是长尾主因。保留的 1787 条收据抽样中，等待开始处理最大 816.93ms、单事件业务最大 87.58ms、批次提交最大 21.45ms，没有覆盖全程 2661.41ms 尖峰。因此下一步应持续归档慢收据与同时间窗数据库等待，并在独立 Linux 环境开启 IO timing 对照，而不是扩大连接池。
4. 压测 PostgreSQL 的 track_io_timing 与 track_wal_io_timing 关闭，WAL/IO 时间为零不能证明无存储等待。存在阻塞会话采样，尚不足以把尖峰单独归因到锁或磁盘。
5. 抽样仅保留最近有限条目，不是完整分布式追踪；2 秒数据库采样可能错过短峰。
6. 需要目标 Linux 和独立发压机，在固定配置下补齐六档、8/24 小时长稳、真实线路/模型、过载降速与恢复闭环，再决定商用容量。当前没有这些环境资料。
7. 上线前需审核并发布明确版本、运行远端 CI、灰度与回滚验证；本地合成结果不能替代生产验收。
