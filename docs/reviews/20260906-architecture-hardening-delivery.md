## 并发和运行层面的补充

- API 的正常回调路径只提交事件与 Outbox，不执行 AI、录音转存或客户回调；独立 worker 最短约 100 毫秒轮询。`TASK_INLINE_EXECUTION_ENABLED` 默认关闭，生产禁止开启。
- 拨号、AI、客户回调、录音、数据清理分别运行。默认每个 worker 的 AI/客户回调/录音执行上限为 4/4/2；跨 worker 通过数据库领取和 Redis 锁协调。任务选取交错租户；低容量租户不再把整个批次的命令并发压到最小值。
- AI/TTS 网络等待前释放读事务；worker 的同步数据库工作使用独立线程与会话。数据库连接池默认每进程 5、额外连接 5，需把 API 和 worker 的进程数一起计入总连接预算。
- 录音转存使用独立磁盘卷 `/var/spool/recordings`，默认最多 2 个下载，检查剩余磁盘。实际验证了 65 MiB 文件转存，超过旧 `/tmp` 的 64 MiB 容量。
- 录音适配器在共享本地卷中保留对象标识、文件锁和删除墓碑，防止调用方超时后旧上传与删除重叠，或重启后重试上传复活已删除对象。生产必须配置持久化 spool；不能给多个独立适配器使用互不共享的生命周期卷。此机制不代表供应商源录音已删除。
- 增加任务最老等待时长与 AI/TTS 最近延迟分位数；分位数是最近 300 秒、每阶段最多 10000 个最新样本的指标，不是全量历史直方图。新增实时队列与客户回调积压告警。

## 本次压测结果及含义

RPS 表示每秒接口请求数。**200 RPS 不等于 200 路并发电话，也不等于每秒拨出 200 通。** 一通电话会产生多个状态、语音和录音事件。

环境：macOS arm64、12 逻辑 CPU；Python 3.12；隔离 PostgreSQL 16、Redis 7；两进程 Uvicorn；无专用 CPU/内存配额。全部使用单独租户的合成通话，从通话中状态转为已完成，走验签、事务写入、分析及 Outbox 入队路径。未经过网关媒体、真实 PBX、云 ASR/TTS/LLM 或客户 HTTP 服务。

| 场景 | 持续时间 | 请求 | 实际吞吐 | P95 | P99 | 结果 |
|---|---:|---:|---:|---:|---:|---|
| 50 RPS 终态回调 | 20 秒 | 1000 | 50.01 RPS | 24.727 ms | 28.934 ms | 1000 个 HTTP 200 |
| 200 RPS 终态回调 | 20 秒 | 4000 | 199.83 RPS | 72.712 ms | 143.130 ms | 4000 个 HTTP 200 |

发送器按预定到达时间生成请求；延迟包含客户端等待，避免闭环发送掩盖排队。两轮最大在途请求分别为 4、35；这也不是通话并发。

核对数据库：5000 条合成通话全部为 COMPLETED，恰好产生 5000 个回调任务。随后通过真实数据库领取/提交路径消费，5000 个任务全部 COMPLETED；连同其他合成夹具共处理 5006 个任务，耗时 12.018 秒。客户回调开关关闭，因此这个消费速度不包括客户接口网络耗时。

这些是短时本地基准，尚未验证 30 分钟至数小时稳态、大数据库、机器资源受限、跨网传输、真实语音及供应商限额下的表现，不应作为采购容量或 SLA 承诺。

可复用工具：`scripts/load-control-api.py`。仅接受回环 IP、演示环境和显式 `--isolated-mock`；凭据通过 `LOAD_WEBHOOK_TOKEN`、`LOAD_WEBHOOK_SECRET` 注入。`--calls-file` 可指定已准备的独立合成通话 ID；不指定时仅覆盖未知通话事件的快速路径，应区别解读。例如：

```sh
python scripts/load-control-api.py --url http://127.0.0.1:19800 \
  --isolated-mock --scenario webhook --rate 50 --seconds 20 \
  --calls-file /path/to/synthetic-call-ids.json --output /path/to/result.json
```

## 升级顺序与正式上线前置条件

1. 在测试部署中先停新拨号、排空当前通话和旧 worker，再备份 PG、语音账本、录音生命周期卷和媒体对象；当前版本不能与不识别 lease_token 的旧 worker 混跑。
2. 执行版本化数据库迁移。旧 SpeechTurn 的 attempt=0 表示未知；不猜测回填。缺失原始 attempt 的旧 AI 任务不会调用模型，需在启用新 worker 前人工核对/废弃；不能通过简单重试把它绑定到新轮次。
3. 平台确认 AI/SMS 实际服务地址，登记客户回调的精确来源及必要私网例外，并校验签名和证书。未登记的旧客户回调将失败关闭，必须在迁移窗口处理。客户接收端需按稳定 Delivery ID 去重：外部投递仍是至少一次，不能保证网络层恰好一次。
4. 按 `.env.example` 更新任务、限流、清理及连接池参数。旧 `.env` 中显式的 3600 秒扫描、10+20 连接池等值不会自动被代码默认值替换。数据库连接预算应覆盖所有 API/worker 进程并为运维保留余量。
5. 录音 spool 使用有容量、权限和备份策略的本地持久卷。默认空间检查按最大录音 × 下载并发 + 128 MiB 余量计算；清理临时数据时保留 `.lifecycle` 墓碑。删除失败保持可见并人工处理，供应商源文件、对象版本和备份另按实际存储策略验收。
6. 当前按单语音网关、单 PBX 归属及已有硬上限交付。不能通过简单增加独立网关副本扩容；多网关路由、分片共享配额和排空切换仍需专门设计及实测。
7. 补齐候选生产环境的真实线路/真机中文多轮通话、客户打断、转人工、短信、录音回听、长时间稳态、供应商限流、重启/断网/数据库切换、备份恢复与回滚演练，再确定通话并发、CPS、RPO/RTO 和 SLA。

## 追加 1000 RPS 测试

见 [1000 RPS 专项结果](20260906-load-1000rps.md)。当前双进程、每进程 10 个最大数据库连接的配置，在 200 个在途请求下出现严重阻塞；这项新增发现尚未修复。此前 50/200 RPS 短测通过不代表 1000 RPS 或生产容量达标。

## 仍未闭环的商业交付项

复审的额外架构事项不等于已全部产品化：多网关水平扩容和高可用部署、PBX/数据库/Redis 故障切换、完整端到端监控、鉴权录音回听、运营商 CDR 对账与正式租户结算，仍需后续实现或外部验收。部分管理 API 仍使用同步 ORM；本次将 worker 工作分流并释放主要 AI/TTS 读事务，没有宣称整个 API 已迁移异步数据库。平台/线路安全上限与 worker 命令并发是不同约束，不能用这次 HTTP RPS 推导全局媒体容量。
