# 单机 500：软件改造及交付验收

日期：2026-10-04，北京时间。基线 GitHub main：`9fcb9f27490b2b8db9b8b3d060b085623fbd6b82`。

**软件交付验收通过。** 最终同一源码的正常、重复和故障注入三组均完成 500 个合成会话、每会话两轮，共 1,000/1,000 条客户可观察的已提交 AI 回复。每组 3,000 个回调、1,000 次成功 AI 指标、1,000 个完成任务，失败指标、客户超时、重复业务回复和过时等待提示均为零，最大任务尝试次数为 1。真实 SIP/RTP、ASR/TTS 音频及目标机容量没有在本次合成测试中验证。

本次交付采用用户后续明确的要求：“本地硬件限制，不能作为验收的卡点……其他的问题是你要解决的问题”。因此独立审查、软件正确性和故障恢复通过后同步源码；本地性能与真实容量资格分别记录。此口径替代 2026-10-03 历史设计/审查中“全容量通过才同步”的交付限制。默认 capacity 模式和生产拨号保护仍然生效；software 模式只调整隔离测试的退出门槛，没有生产绕行开关。

## 方案与改造

架构设计及实施前自评见 [架构方案](20261003-single-host-500-design.md)。单机保留单 PBX 控制者、12 个媒体进程共 600 槽位、4 个独立 AI worker 共 640 槽位、6 个 API 和 6 个持久回调消费者，应用数据库总连接预算 64。指定 AI worker 身份、代次和 TTL 心跳与实际新拨号准入关联；缺失/损坏心跳、领取失败或已到期 AI 队列积压会暂停新拨号。账号配额、未知外部结果、通话保序及数据库锁顺序继续作为业务边界。

软件瓶颈修复经过可实施性评估及独立审查后实施：

- 模型等待在 liveness 查询之后、等待提示准备排队之后分别重新检查模型是否已完成，完成后不再开始发送过时提示。
- 常规 AI 回复的数据库工作池调度从 7 次减到 4 次，保持各自的事务、fresh call/sequence、租约检查及持久 action 重放；网络等待继续在有界协程中执行。最终每组记录 4,000 次常规任务调度；基线含提示共 8,236 次。单个合并工作单元的排队峰值仍高，不能宣称每阶段 P99 都下降，也不能把阶段 P99 相加当回复时延。
- Agent 的模型连接错误曾导致一组只有 998 条回复、1 个死信。现在只对纯模型 ConnectError/ReadError/RemoteProtocolError 重试一次，原总截止时间覆盖两次尝试及退避，每次尝试重新占用账号额度。HTTP 拒绝、超时、无效回复不自动重试；播放、挂断、短信没有复用此模型重试规则。
- 回复观测器按 call/attempt/sequence 匹配，只完成已登记的轮次；读库故障显式失败。45 秒客户等待上限保留，超时保存通话、转录、实时序号和任务快照。测量期间源码摘要必须保持一致。

## 独立审查和回归

[初始候选审查](20261003-single-host-500-independent-review.md)、[最终增量审查](20261004-single-host-500-software-independent-review.md)及[独立证据复核](20261004-single-host-500-software-evidence-review.md)均无阻断 P0/P1。取消/租约失效发生在两次提交之间、prepared 未提交时的未知 HTTP 结果重放、模型在两种排队窗口完成、模型失败、配额拒绝及取消/截止时间均有回归覆盖。独立证据复核核验了最终三组同源码、逐通话两轮结果、原始 P99、失败记录保留和仅归档复算一致；报告中的摘要为追加复核报告前的证据快照。代码审查者没有代替作者执行测试。

最终后端 PostgreSQL 回归 338 项通过；唯一跳过的 Redis 续期/互斥用例单独补跑通过，合计 339 项。Agent 25 项、工具 33 项通过。SQLite 定向阶段 32 项通过，Redis 相关覆盖在上述后续环境完成。首次完整回归的三项失败是测试残留活动通话及新工作树缺前端构建产物；清理修复经独立审查，全新数据库重跑通过。未改动的 33 个前端源码文件与此前已验证构建一致，构建产物来源及摘要另有记录。本次没有声称重新执行未修改的前端、网关或录音全套测试。

## 全部 500 路测试结果

负载固定为 500 个会话、两轮、125 个初始终句/秒、轮间计划间隔 4 秒；模型延迟 3 秒、播放确认延迟 0.2 秒。基线 2 与最终三组使用一致的六个观测/负载文件、依赖和进程拓扑。最终三组 115 项运行源码摘要完全相同，软件模式与 capacity 的实际结果均保存。

| 轮次 | 代码阶段 | 观察回复 | 回复 P99 秒 | 等待提示 | 模型传输重试 | 软件结果 |
|---|---|---:|---:|---:|---:|---|
| baseline1 | 初始基线 | 1000 | 34.31 | 377 | 0 | 通过 |
| fixed1 | 工作池及首个提示检查 | 1000 | 26.39 | 0 | 0 | 通过 |
| fixed2 | Agent 恢复修复前 | 998 | 27.13 | 1 | 0 | 失败，保留原记录 |
| baseline2 | 最终观测工具的基线 | 1000 | 31.95 | 412 | 0 | 通过 |
| fixed3 | Agent 恢复修复后 | 1000 | 26.18 | 0 | 1 | 通过 |
| fixed4 | 提示准备检查前的重复轮 | 1000 | 29.07 | 30 | 0 | 通过 |
| fixed5 | 最终正常轮 | 1000 | 29.66 | 0 | 0 | 通过 |
| fixed6 | 最终重复轮 | 1000 | 27.57 | 0 | 0 | 通过 |
| fault7 | 最终故障注入轮 | 1000 | 30.94 | 0 | 3 | 通过 |

正常最终两轮相对 baseline2 的 P99 改善分别为 **7.17% 与 13.71%**，只适用于这些实测轮次。fault7 实际仅注入 1 次发送前 ReadError，另外发生 2 次自然传输错误，总共 3 次 Agent 重试、0 次后端模型传输重试；所有业务回复及任务均成功且没有任务重试。fixed3 也曾自然遇到一次 ReadError 并恢复。故障注入结果不是宣称任意故障都能恢复。

全部轮次的 capacity_slo_passed、load_validity_passed、conversation_control_slo_passed 均为 false，不能把 software 的退出 0 当真实 500 路或计划 125 轮/秒验收通过。当前环境及模拟播放没有提供真实音频容量、时延或长稳证据。这些实际结果保留，并依用户明确要求不阻塞软件交付。
