# 数据库工作池排队与回调延迟优化

2026-09-16。本次在已有未提交改动上增量优化，保留原有改动。未 commit、push 或替换业务实例。

## 风险依据与修改范围

此前隔离压测的 80 轮/秒回复 P99 为 7.63 秒，数据库工作池阶段排队 P99 约 0.75–1.21 秒；600 回调/秒的 Inbox 完成最大延迟为 2.16 秒。后者尚未证明由单一数据库锁或 checkpoint 原因引起。本次不改变时延门槛、工作线程数量和数据库连接配置。

| 文件 | 本次增量修改 | 保留的约束 |
|---|---|---|
| `backend/app/services/task_queue.py` | PostgreSQL 已锁定任务用一次 CASE UPDATE 批量领取；空容量直接返回 | 各任务独立 lease token；租户轮转、同通话 FIFO、SKIP LOCKED、最后一次失败恢复保留；SQLite 保留原条件更新 |
| `backend/app/services/async_ai.py` | 合并轮询间隔内陆续释放的槽位，不再每完成一个任务就立即领取；失败轮询同样受间隔约束，并与健康信号的成功领取时间分开记录 | 只领取空闲槽位，保留续租和取消栅栏；新增任务最多增加一个配置轮询间隔的调度等待 |
| `backend/app/services/ai_liveness.py` | 状态查询从排队到执行始终只保留一个活动批次，新请求合并进下一批；丢弃已取消等待者 | 不缓存历史查询结果；最终动作、attempt/turn 和落库检查不变；单批错误不阻塞后续批次 |
| `backend/app/services/callback_inbox.py` | 一个 SQL 查询同时识别存在的通话及可锁通话；整组跳过被锁通话的事件 | 同一通话不越序、不因锁冲突增加失败次数；不存在的通话仍交原处理器处理；业务、Outbox、回调完成标记及计数在原事务内提交 |
| `backend/tests/test_queue_pressure.py` | 增加六项调度、批处理、领取失败健康信号和真实 PostgreSQL 行锁回归 | 40 个任务只发出一次领取 UPDATE，且令牌各不相同；锁释放后同通话事件按原顺序补处理 |

## 页面、入口及状态清单

本次无前端页面或路由修改。影响入口是后台 AI 任务领取、模型等待状态检查，以及状态、转写、语音、按键、媒体和录音回调及批量回调。

验证状态包括 pending/processing/failed/dead/completed、重复事件、事务回滚、数据库锁冲突、通话结束、模型失败、动作重试及取消。回归覆盖回调持久接收 → 有序消费 → AI 任务 → 动作与结果落库；压测中的模型和播放为模拟实现。

浏览器实测覆盖管理员菜单点击、路由内容、返回首页、登录退出、错误登录、角色权限、联系人保存/搜索/重载回显、任务客户选择和分页、通话分页、知识及跟进保存、业务策略保存与过期发布拒绝、流程编辑和计费说明。项目不含门店、房型、购物车、下单及支付页面，所给电商验收链路不适用。

## 压测口径

使用已有固定依赖镜像 `sha256:ca41a633aea2de84671ed13582538f6dbda7067adb040a347193a8167d7b38df`，源码只读挂载。每档创建独立 PostgreSQL、Redis 和测试进程拓扑；500 个合成会话。对话档 80 轮/秒、5 轮、间隔 6.25 秒；回调档 600 事件/秒、120 秒。云模型固定模拟等待 3 秒、播放模拟等待 0.2 秒。回复门槛 4.2 秒，回调相关门槛 1 秒。

第一版两个锁查询的试跑证据保留在 `single500-0916-queueopt-*`：80 档回复 P99 4.678 秒，回调投递最大 126.6ms，Inbox 完成最大 215.3ms；600 档投递最大 1421.2ms、Inbox 完成最大 4335.7ms。两档数据完整性通过，时延门槛未全部通过。此结果不能隐藏；最终版本将锁识别合并成一个 SQL，另用 `single500-0916-queueopt-v2-*` 记录复测。

最终 80 档：7,500 个回调和 2,500 个 AI 任务全部完成；回复 P99 **3941.83ms**、投递最大 **103.73ms**、Inbox 完成最大 **228.11ms**；截止时间错过数为零，数据完整性与本档时延门槛通过。四个 AI worker 的准备阶段排队 P99 为 **146.42–166.89ms**，历史同档为 887.93–1197.25ms；领取执行 P99 为 23.42–40.63ms，历史为 73.18–112.19ms。这是单轮观察，不是长期容量承诺。

80 档最终证据：[结果 JSON](evidence/20260913-single-host-500-fixes/single500-0916-queueopt-v2-dialogue80-results.json)。原始日志与阶段快照保留在 `artifacts/single-host-500/single500-0916-queueopt-v2-dialogue80*`。

最终 600 档：120 秒处理 **72,000 个回调、24,000 个 AI 任务**，全部完成；投递最大 **267.39ms**、Inbox 完成最大 **757.31ms**，无积压、无死信，本档数据完整性及 1 秒时延门槛通过。证据：[结果 JSON](evidence/20260913-single-host-500-fixes/single500-0916-queueopt-v2-callback600-results.json)。四次试跑的临时容器、网络和卷已核对清理，独立 PostgreSQL 回归容器和浏览器测试 API 也已停止。

版本边界：以上两档通过结果对应 v2 压测源码，测试中源码哈希未变化。压测后收尾审查仅将 `async_ai.py` 的轮询尝试时间与成功时间分开，防止数据库领取失败误刷新健康信号，并新增故障回归；最终代码全量测试通过，但此健康判断修复后未再重复完整压测。测量版与最终版哈希、结果摘要见[汇总证据](evidence/20260916-db-queue-optimization.json)。

已知限制：第一版试跑曾超标，最终通过数据仍只有每档一轮，尚不足以证明长时间高负载稳定。1200 回调/秒及 100/125 轮对话/秒未在本次复测；没有证据将这些档位标记为已修复或容量通过。
