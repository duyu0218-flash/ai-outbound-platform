# 1000 RPS 专项压测

**结论：未通过。当前双进程 API 配置不能承诺 1000 RPS。** 此前 200 RPS 短时测试全部成功，本轮更高到达负载触发严重阻塞；降低在途请求数后恢复响应，但实际处理速度仍远低于 1000 RPS。

所有测试只针对本轮建立的 localhost mock 服务、独立 PostgreSQL/Redis 和合成通话。没有真实拨号、真实短信或生产发布。仅修改了压测工具的排队超时与增量统计，**尚未修改应用代码解决这次新发现的阻塞问题**。

## 环境与方法

- 同一 macOS arm64、12 逻辑 CPU；Python 3.12、两个 Uvicorn worker、PostgreSQL 16、Redis 7。
- 每个 API 进程数据库池默认 5 + 5，最多合计 20 个 API 数据库连接。
- 签名通话结束事件：已有合成通话从 IN_HUMAN 转为 COMPLETED，涉及事务、事件记录、分析与 Outbox 入队。未启动消费者，以便核对入队总数。
- 正式测试只把**测试实例**的控制回调配额提高到每分钟 120000 次，避免默认每分钟 6000 次限额干扰。仓库和业务环境的默认限额未更改；正式结果没有 HTTP 429。
- 发送器采用预定到达时间，最大在途请求 200，HTTP 超时 10 秒，客户端等待发送槽位最多 5 秒。无法取得槽位的请求记为 `generator_queue_timeout`，没有发送到服务器，不能算成服务器收到的请求。
- 首次默认限额快速路径试压出现长队列后中止，无完整客户端结果，不用于下表。随后给工具增加排队超时及每秒增量落盘，再正式测试。

## 正式测试：1000 RPS 到达，持续 20 秒

| 项目 | 结果 |
|---|---:|
| 计划到达请求 | 20000 |
| 实际发出的请求 | 633 |
| 收到 HTTP 200 | 33 |
| 已发出但客户端 10 秒读超时 | 600 |
| 发送端排队超时、未发出 | 19367 |
| 最大在途请求 | 200 |
| 含收尾的总耗时 | 30.447 秒 |
| 成功请求 HTTP P95 / P99 | 317.800 / 326.313 毫秒 |
| 包含排队与失败的到达至结束 P95 / P99 | 5001.858 / 15008.366 毫秒 |

后两种延迟口径不能混用。仅 33 个成功响应的延迟不代表全部请求，更不能用这个分位数声称 1000 RPS 已达标。客户端在途上限用尽后大量请求未发出，因此本轮是“1000 RPS 提供负载下失败”，不是服务器持续收到并处理了 1000 RPS。

客户端结果之外，服务日志出现大量 15 秒 HTTP 504。数据库实际提交了 53 条终态及 53 个对应 Outbox 任务，而客户端只收到了 33 个成功响应。**超时不等于业务未提交**，重试必须复用事件标识、依赖服务端去重，不能生成一个新的业务操作。

## 对照：仍按 1000 RPS 到达，但最多 32 个在途请求

配置、机器与业务路径保持一致，重新启动隔离 API，使用另一批未结束的合成通话；此轮持续 5 秒。

| 项目 | 结果 |
|---|---:|
| 计划到达请求 | 5000 |
| 实际发出 / HTTP 200 | 2269 / 2269 |
| 客户端读超时 | 0 |
| 发送端排队超时、未发出 | 2731 |
| 总耗时 | 10.078 秒 |
| 按含收尾时间计算的成功吞吐 | 225.15 RPS |
| 成功 HTTP P95 / P99 | 190.091 / 229.533 毫秒 |

这个对照说明，压低在途请求后可以避免本轮观察到的严重阻塞；仍有超过一半的计划请求未能发出，**不能认定支持 1000 RPS**。225.15 RPS 也不是已验定的系统最大容量，只是这一轮的测量值。

数据库复核：对照后共 2322 条 COMPLETED 与 2322 个 Outbox，等于此前 53 条加本轮 2269 条；未观察到这批终态与入队数量不一致。

## 瓶颈证据与下一步

高并发阻塞时，隔离 PostgreSQL 中 20 个 API 连接均处于 `idle / ClientRead`，没有形成大量正在执行的慢 SQL。结合 `backend/app/db.py:get_webhook_session` 在同步依赖中先取得连接、再交给同步路由使用的实现，以及 32 在途请求对照恢复响应，主要风险指向**同步线程调度与数据库连接占用之间的相互等待**。本轮没有取得完整线程栈，精确根因仍需用线程栈与各阶段等待指标最终确认，不能简单归因于数据库 CPU 不足。

建议处理顺序：

1. 在进入同步依赖、占用数据库连接之前实施有界请求准入；超过预算快速返回带 Retry-After 的可重试响应，避免无限排队和重试放大。
2. 调整事务与线程归属，让连接获取、路由事务和释放在同一个受控执行单元完成；或迁移真正异步数据库。不能仅盲目增加连接池或 API 副本。
3. 补充连接池等待、借出连接、线程占用、接口在途、超时后提交和重复回调指标，验证过载后能自主恢复。
4. 修复后按 200 / 400 / 600 / 800 / 1000 RPS 阶梯复测，至少增加 30 分钟稳态、故障恢复和大数据库场景；再确定可对外承诺的容量。
