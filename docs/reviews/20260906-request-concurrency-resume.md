## 修复内容

- 普通 API 与 Webhook 共享每进程准入总预算，默认按连接池预算设置；默认不等待，满额返回 `503 + Retry-After`。可选等待队列有数量和时间上限。拒绝发生在进入数据库依赖和同步业务线程之前。
- Webhook 会话延迟取连接。六个回调入口的业务处理、外层事务提交和连接归还在同一次同步执行中完成；保留事件去重、业务状态、Outbox 原子提交与已有保存点回滚语义。
- 请求超时发送 504 后仍持有执行名额，等实际同步事务及清理结束后才释放。超时并不意味着数据库一定没提交，调用方应沿用同一事件标识重试。
- `/metrics/runtime` 认证后无需数据库即可读取连接池等待/借出、线程令牌、回调执行线程、在途请求、拒绝、重复事件和超时后提交尝试指标。后者记录提交事件触发，不能单凭该计数证明事务提交成功。
- 坐席 NDJSON 事件流单独限额，默认每进程 64 条；流开始前释放认证查询会话，快照查询并发默认 2。避免长连接耗尽普通 API 名额或长期占有认证事务。
- 压测器按到达时间创建有限数量任务，独立记录发压漏发、队列饱和、客户端错误和成功吞吐；测试使用已存在且互不相同的合成通话，成功回调必须执行真实数据库写入。

主要文件：`backend/app/db.py`、`middleware.py`、`main.py`、`config.py`、`api/routers/webhooks.py`、`api/routers/webrtc.py`、`services/runtime_metrics.py`、`backend/tests/test_request_execution.py`、`.env.example`、`scripts/load-control-api.py`。

## 容量与数据对账

最终数据核对已完成，容量未通过。隔离环境为 macOS 上两个 Python API 进程、Docker PostgreSQL 16/Redis 7，API 每进程最多 10 个数据库连接，压测器并发上限 200。Docker 可用 12 CPU、约 7.75 GiB 内存；服务与发压器共享主机，存在其他负载。本轮不执行 Outbox 消费或任何真实线路、AI、短信、客户回调。最终数据库含 100 万联系人、90.6 万通话，数据库大小约 1520 MB。

冻结代码的每级 20 秒阶梯结果如下。成功 RPS 按实际耗时计算，503 不计成功。各级均实际发送全部计划请求，没有客户端错误或发压丢弃，仍未达到计划成功量。

| 目标 RPS | 计划请求 | HTTP 200 | HTTP 503 | 成功 RPS | 成功响应 P95 ms |
|---|---:|---:|---:|---:|---:|
| 200 | 4000 | 3965 | 35 | 198.12 | 63.052 |
| 400 | 8000 | 4327 | 3673 | 215.77 | 124.081 |
| 600 | 12000 | 4354 | 7646 | 217.30 | 120.163 |
| 800 | 16000 | 4318 | 11682 | 215.35 | 125.119 |
| 1000 | 20000 | 4362 | 15638 | 217.63 | 124.623 |

200 RPS 长时观察：程序计时 1800.016 秒，计划 360000 次、实际发送 329672 次。200 为 277740 次、503 为 51900 次、发压漏发 30328 次、ReadTimeout 30 次、ReadError 2 次；成功吞吐 154.30 RPS。成功响应 P95 为 190.339 ms，但包括计划漏发在内的计划到完成 P95 为 33997.162 ms，不能只展示成功响应延迟。

五级阶梯的 HTTP 200 数量与完成通话、独立事件、唯一 Outbox 任务数量逐级一致。长时观察中完成通话、事件、任务均为 277769，较 HTTP 200 多 29；没有重复投递计数或重复任务键。此处是聚合对账，压测器没有保存逐请求响应日志，尚不能把这 29 条逐一映射到客户端错误，不把聚合计数当成逐事件完整证明。两个 API 进程结束后借出连接、回调执行线程、普通/回调在途、AnyIO 等待任务均为 0；探针在途 1 是本次指标读取自身。

最终应用、测试和压测脚本与压测开始时 `source-manifest.json` 的哈希一致。证据为 `final-code/step*.json`、`steady.json`、`final-verification.json`，全部保存在本地证据目录中。

验收后已停止本轮隔离 API/监测进程，删除 `codex-resume-pg-0906`、`codex-resume-redis-0906`、`codex-resume-fault-redis-0906` 临时容器及其匿名卷。合成数据库已清理，测试脚本、结果和日志保留；原业务容器未替换。

持续测试监测中出现约 677 秒的墙钟采样空档，发压程序记录了计划漏发；程序有效计时与墙钟时长不一致。原因尚未定位，因此本轮只能作为长时运行与恢复观察，不能算无中断的稳态容量认证。采样显示每进程借出连接与回调线程最高达到 10，未观察到连接池获取失败，AnyIO 等待任务采样为 0；采样不能排除未观测时间的瞬时变化。

对账首次并行大表查询触及隔离 PostgreSQL 容器的共享内存限制，报 `could not resize shared memory segment`；仅在对账会话执行 `SET LOCAL max_parallel_workers_per_gather = 0` 后完成只读核验，没有修改压测服务或数据库全局设置。生产规划需单独核算共享内存，不能把这个临时容器配置作为生产规格。原错误及串行核验日志均保留。

原先短阶梯测试在 1000 RPS 到达计划下，20000 次请求中 4519 次 200、15480 次 503、1 次 ReadError，含尾部等待成功吞吐约 202.71 RPS。这份数据早于坐席流隔离修复，仅作历史对照；本节表格为最终冻结代码复测。`pre-stream-isolation/` 保存修复前未跑完的稳态，`generator-diagnostic/` 保存发压器自身饱和的早期试验，都不能替代最终验收。

## 故障与恢复

故障注入只作用于自建隔离 Redis 容器和 `resume_fault` 数据库连接。生产模式 Redis 失败关闭策略通过测试夹具启用，不使用生产账号。

- Redis 中断的 20 次请求均返回可重试 503，恢复后首次成功用时约 0.837 秒，原事件重试成功。
- 三次定向断开数据库连接，共终止 15 个连接；200 次请求中 190 次 200、10 次 500。同一事件标识重放 200 次全部成功，重放耗时约 1.876 秒。
- 最终 230 条完成通话、230 条独立事件和 230 条 Outbox 一致，未出现重复任务。运行指标回到连接 0、回调线程 0、回调在途 0。未验证外部供应商的幂等业务效果。
- 该故障运行早于坐席事件流隔离修复，回调事务和准入实现相同；不把它表述为所有最终源码场景已完整故障复测。证据为 `fault-recovery.json`。

## 已知问题、环境限制与上线条件

1. 1000 RPS 尚未达标；限额拒绝是过载保护，不计成功。当前环境也不能证明生产容量。发压漏发、超时和依赖抖动必须单列。
2. 数据库连接中断仍可能返回 500；已验证同事件重试可恢复。HTTP 超时后的实际提交需要按事件对账，不能假设失败响应等于无业务效果。
3. Outbox 消费在本轮吞吐测试中关闭，持续增长是测试设置。尚未证明分析、回调、录音等消费者能持续消化 1000 RPS 对应任务；不能据入口入队量声称端到端完成。
4. 事务优化候选未采用：相同 Outbox 键的并发插入会回滚此前状态。必须先解决局部冲突回滚，再减少保存点和重复查询。
5. 正式上线前需备份并执行已有 `20260906_execution_leases.sql` 迁移，核算所有 API/worker 连接预算，部署独立消费者、持久化录音卷，配置服务凭据和回调来源，验证告警、回滚及故障恢复。
6. 目标环境需重跑有效 1000 RPS 至少 30 分钟，并确认成功响应/数据库/消费者完成量与延迟均达标，队列不持续增长。真实线路、PBX、ASR/TTS/LLM、录音回听与真机媒体链路另验。
